# 노션 반영 요약 (1~9단계 + 홈페이지·DIRECT 경로)

구현하면서 **명세(계약·스키마·동작)를 바꾼 결정만** 노션 문서별로 묶었다.
구현 세부·내부 구조는 제외했다. 괄호 안은 `docs/DECISIONS.md`의 항목 번호다.

## 1. API 명세 (「인증 수탁사 통합」 API 문서)

### 거래소 ↔ A사 서명 (가장 먼저 합의할 것)
- `X-Signature = hex(HMAC-SHA256(key=HMAC Secret, msg=X-Timestamp 바이트 + 원본 본문 바이트))`.
  구분자 없음, **소문자 hex**, 본문 없는 GET은 빈 바이트, 키는 **Secret 문자열의 UTF-8 바이트**.
  `X-Timestamp`는 유닉스 초, 허용 오차 ±300초. (0.1절)
- 기준값(거래소 구현 검증용): `secret="test-secret"`, `ts="1700000000"`,
  `body={"client_user_ref":"u-1"}` → `8d15772196338b56f028ea824940d5cfa11c3716ec0d7cf57675a81d63d071a8`
  / 빈 본문 → `1b74eaf87da46877ba651ac812b24a3bf01990e9ed0101b88268f60f965729e2`. (0.1절)
- 알려진 한계 2개를 문서에 남긴다: ① 메서드·경로를 서명하지 않아 본문 없는 GET 서명은 5분 안에 다른
  경로로 재사용 가능 ② 타임스탬프와 본문 사이에 구분자가 없다. (0.1절)
- **웹훅 헤더는 `X-Timestamp`, `X-Signature`, `Content-Type`만** 보낸다(`X-Api-Key`는 없다).
  거래소는 **받은 본문 바이트 그대로** 검증해야 한다(재직렬화하면 서명이 깨진다). (D31)

### IA-01 인증 요청
- 응답 코드를 둘로 나눈다: **201** 새 건 / **200** 진행 중인 기존 건을 돌려준 경우.
  200일 때 `verification_id`·`expires_at`은 그대로이고 **인증창 토큰만 새로 발급**된다
  (이전 토큰과 이미 열려 있던 인증창은 그 시점에 무효). 거래소는 둘 다 성공으로 보고 `auth_url`로 보낸다. (D12, D7)
- `EKYC_ENV=production`에서는 `return_url`·`callback_url`에 **https만** 허용한다. (D29)
- 허용 IP가 아닌 곳에서 온 요청은 **403**(API Key·서명·타임스탬프 실패는 401)으로 구분한다. (D33)

### IA-02 인증창 진입
- 인증창 토큰 형식은 `{만료 유닉스초}.{임의값}`이고 서버는 토큰 전체의 sha256만 보관한다.
  별도 컬럼 없이 10분 제한이 성립한다. (D36)
- 없는 토큰·이미 쓴 토큰·만료 토큰을 구분하지 않고 **모두 410**으로 답한다. (D36)
- 진행 중인 건에 토큰을 재발급해 다시 들어오면 **그 건의 현재 stage 화면**으로 보낸다. (D34)

### IA-04 / IA-06 휴대폰
- 명의 대조 실패 응답은 기본(양호)에서 **HTTP 200 + 같은 문구 1종**이다(불일치 사유를 구분하지 않음).
  `VULN_W14`를 켜면 400(명의 불일치)·404(미등록 번호)로 갈라진다 — 이 차이가 W-14 진단 증적이다. (D45, D1)
- 인증번호 발송 **429 조건이 두 가지**다: ① 60초 이내 재요청 ② 건당 발송 5회 초과.
  ②를 넘겨도 건은 종결하지 않는다. (D11)
- 인증번호 **만료·형식 오류는 시도 횟수(3회)에 넣지 않는다**. 불일치만 센다. (D49)

### MC-01 / MC-02 (모의 통신사)
- MC-01은 내부용 `reason`(`NAME_MISMATCH` / `NOT_SUBSCRIBER`)을 돌려주고, A사가 기본값에서 P01로 합친다. (D1)
- MC-02의 토큰 거부는 사유를 구분하지 않고 **모두 409**다(없음·사용됨·만료·다른 건의 토큰). (D50)

### MC-03 (모의 통신사, 신규)

- `POST /carrier/v1/device-registrations` 추가. 본인확인 앱(PASS) 기기 등록 전 명의 확인이다.
  요청 `{phone_number, name, birth_date}`, 응답 `{matched, reason}`.
- MC-01과 다른 점: **생년월일까지 대조**하고 **대조 토큰을 주지 않는다**. CI 발급으로 이어지지 않는다.
- A사 쪽 짝은 `POST /test-inbox/devices`(실습 전용). 통과하면 수신함 키를 새로 발급하고
  번호당 기기 하나만 유효하게 둔다. (D85)

### IA-21 / IA-22 (신규, 선택 경로)

- 위탁사가 인증 화면을 직접 만드는 방식을 **추가**했다. IA-01에 `mode: "DIRECT"`를 주면
  `auth_url` 없이 `verification_id`만 돌려주고, 아래 두 경로로 제출받는다.
  - `POST /api/v1/verifications/{id}/id-card` — 신분증 이미지(base64) + 성명·주민번호·발급일자 + **CI(필수)**
  - `POST /api/v1/verifications/{id}/face` — 얼굴 이미지(base64) → 최종 판정
- 이미지는 JSON 본문에 base64로 담는다(기존 서명 규칙을 그대로 쓰기 위해).
- 재시도 가능한 실패(E01~E05)는 400, 판정 확정(OK·X01·E06)은 200 + 웹훅과 같은 본문.
- 기존 `mode: "REDIRECT"`(기본)는 그대로다. **현재 연동은 바꿀 것이 없다.** (D87)
- 이 방식을 쓰면 주민등록번호·신분증 사진을 **위탁사가 직접 수집**하게 되어 동의 수집·안전조치
  책임이 위탁사로 옮겨간다. 위탁/수탁 경계와 처리방침을 함께 손봐야 한다.

### IA-09 / IA-12
- IA-09 성공은 `/verify/result`(결과 화면)로 보내고 그 화면의 버튼으로 `return_url`로 돌아간다.
  그 외 종결(취소·P01~P05·E06·X01)은 `return_url`로 바로 보낸다. (D64)
- IA-12는 **진행 중인 건도 조회**할 수 있다(`status=PENDING`). 어떤 경우에도 주민번호·이미지는 넣지 않는다. (D66)

## 2. DB 설계 (테이블 정의서)

### 컬럼 추가·변경

- **`verifications.mode`** 추가: `REDIRECT`(기본, 기존 인증창) / `DIRECT`(위탁사 화면 + 서버 간 API).
  CHECK 제약. DIRECT 건은 인증창 토큰을 만들지 않고 stage를 `ID_CARD`에서 시작한다. (D87)
- **`site_inquiries` · `site_documents` 추가**: 회사 홈페이지 전용. 11장 13개와 별개로 센다.
  `site_documents.filename`은 파일 이름만 담고 경로 구분자·`..`를 CHECK로 막는다. (D90)
| 테이블 | 변경 | 이유 |
|---|---|---|
| `verifications` | **`entry_nonce`** 추가 | 토큰 재발급 시 이미 열려 있던 인증창을 410으로 막는다 (D7) |
| `verifications` | **`last_error_code`** 추가 (NULL 허용, 10장 코드 CHECK) | 진행 중 실패 코드(P01, E01~E05)를 남긴다. `reason_code`는 종결 시에만 (D8) |
| `id_documents` | `rrn_enc`·`birth_date`·`issue_date`를 **NULL 허용**으로 | 행을 IA-07(이미지 업로드)에서 만들기 위해 (D41) |
| `id_documents` | CHECK 추가: `ci_matched IS NULL OR (세 컬럼 NOT NULL)` | X-01까지 간 건에는 값이 반드시 있다 (D41) |
| `id_documents` | `mois_matched` 추가 | 진위확인 결과 증적·관리자 표시 (D4) |
| `clients`·`admins` | `allowed_ips`를 **JSON 배열**로 | 운영은 PostgreSQL, 테스트는 SQLite로 같은 모델을 쓴다 (D20) |

### 제약·규칙
- 명세가 PK를 적지 않은 6개 테이블(`consents`, `callbacks`, `access_logs`, `phone_events`,
  `face_checks`, `mock_mois_registry`)에 `id` 대리 키를 둔다.
  `consents`는 `UNIQUE(verification_id, type)`, `mock_mois_registry`는 `UNIQUE(rrn_hash)`. (D26)
- CHECK 3개를 추가했다: ① 진행 중에는 `reason_code` NULL, 종결되면 NOT NULL
  ② `access_logs`의 `HISTORY_DOWNLOAD`·`IMAGE_VIEW`는 `reason` 필수
  ③ `phone_events`의 `name_mask`·`phone_mask`는 `IDENTITY_MATCH`에서만 NOT NULL 가능. (D27)
- **모든 시각 컬럼은 tz 없는 UTC**로 저장하고, 화면·웹훅·API에서 KST(`+09:00`)로 바꿔 내보낸다. (D23)
- 암호문은 **행 식별자로 AAD를 묶는다**(`테이블:컬럼:행 식별자`). 다른 행의 암호문을 복사해 넣으면
  복호화가 실패한다. 적용 대상: `id_documents.rrn_enc`, `phone_verifications.match_token_enc`,
  `phone_otps.inbox_ciphertext`, `admins.otp_secret`, 통신사 `subscriber.rrn_ciphertext`. (D17)

### 시크릿 목록 추가 (12장)
- `ekyc/admin-otp-key` — 관리자 TOTP 시크릿 암호화용(주민번호 키를 재사용하지 않는다). (D25)
- `carrier/subscriber-key` — 통신사가 가입자 번호·성명을 HMAC하는 자체 키. (D42)

## 3. 요구사항·기능 정의 (판정 사유 코드·단계 정의)

- **E06 경계**: "3회 초과"를 **"3회 도달"**로 읽는다. E01~E05 실패를 `face_attempts` 하나에 합산하고
  **3번째 실패 응답이 곧 E06 종결**이다(값 최대 3, CHECK `0~3` 유지). X01은 이 카운터와 무관하다. (D10)
- **E02 범위**: 주민번호 7번째 자리는 **1~4만 유효**(외국인·1800년대 코드는 E02), 생년월일은 실제 달력
  날짜여야 하고, 발급일자는 `YYYY-MM-DD` 고정 + 미래·생년월일 이전 거부. 모두 E02이며 시도에 포함한다. (D9)
- **E01 vs E04**: 신분증 사진의 얼굴 수 문제(0개·2개 이상)는 **E01**, E04는 얼굴 단계 전용이다.
  셀카의 형식·용량 오류도 E01로 묶는다. (D57, D62)
- **E03 사유 비공개**: 미등록·이름 불일치·발급일자 불일치·분실을 구분하지 않고 모두 E03 하나로 보여준다. (D60)
- **이미지 수명**:
  - IA-07 시점에 `id_documents` 행을 만든다. 업로드 직후 이탈·만료된 건의 이미지도 DB로 추적돼야
    파기 배치가 지울 수 있고, 그래야 `VULN_C10`의 양호/취약 차이를 증적으로 보여줄 수 있다. (D41)
  - 재업로드 때는 `s3_key`를 새 파일로 바꾸고 **이전 파일을 즉시 삭제**한다. (D41)
  - E01로 거부된 이미지는 **저장하지 않는다**. (D58)
  - 셀카는 시도마다 `face_checks` 행을 남기고 **판정 직후 파일을 지운다**. (D67)
  - 성공뿐 아니라 **모든 종결 경로**에서 남은 이미지를 파기한다. (D63)
- **X01 증적**: X-01 불일치로 즉시 종결하더라도 입력된 주민번호를 암호문으로 남긴다
  (관리자 상세 표시 + CHECK 충족). 보관기한이 지나면 파기 배치가 지운다. (D59)
- **동의**: 약관 버전은 화면에 내보낸 값과 서버 값을 대조하고, 다르면 400으로 다시 받는다.
  기록에는 항상 서버 값을 쓴다. (D40)
- **인증번호 중복 제출**: 같은(맞는) 인증번호가 동시에 들어오거나 확인 버튼을 두 번 누르면
  한쪽만 성공한다. 진 쪽은 **불일치로 세지 않는다** — 시도 횟수를 깎지 않고 현재 단계로 돌려보낸다.
  예전에는 이 경로가 불일치로 세어져 **맞는 번호를 넣고도 P02로 종결**될 수 있었다. (D88)
- **화면 문구는 존댓말(\~습니다 / \~해 주세요)로 쓴다.** 이용자·관리자·연동 담당자가 보는 문구 전부가
  대상이다(홈페이지·인증창·오류 화면·관리자 콘솔·API 오류 메시지). 코드 주석과 설계 문서는 제외. (D86)

### 취약 플래그 6개 (14장)

기본값은 전부 꺼짐이고, 플래그마다 "기본값에서는 막힌다 / 켜면 뚫린다" 테스트 쌍이 있다.
넘지 말아야 하는 선도 함께 고정했다 — 예를 들어 `VULN_W09`를 켜도 **X-01 CI 대조 통과는 항상 요구**한다. (D80~D82)

| 플래그 | 켜면 |
|---|---|
| `VULN_W08` | IA-12가 다른 위탁사 건도 돌려준다 (**제출 경로에는 적용되지 않는다**) |
| `VULN_W09` | 얼굴 단계의 stage 검사와 진위확인 통과 확인이 빠진다 |
| `VULN_W10` | 관리자 목록 JSON이 주민번호 원문을 돌려준다 (화면은 계속 마스킹) |
| `VULN_W14` | 명의 불일치와 미등록 번호를 다른 메시지·HTTP 상태로 구분해 보여준다 |
| `VULN_W17` | 마스킹 필터를 걸지 않은 로거로 인증번호·번호 원문을 남긴다 |
| `VULN_C10` | 파기 배치가 DB 참조만 지우고 저장소 파일은 남긴다 |

**홈페이지 자료실·문의에서만 쓰는 웹 점검용 3개 (D90)** — 금취분평 웹 항목을 재현할 대상이
없어서 추가했다. 번호는 14장 양호 통제 번호를 그대로 따른다.

| 플래그 | 양호(기본) | 켰을 때 |
|---|---|---|
| `VULN_W01` | 자료실 검색이 바인딩 파라미터 | 검색어를 SQL에 이어 붙임 → SQL 인젝션 |
| `VULN_W02` | 관리자 문의 상세가 autoescape | `\| safe` 출력 → 저장형 XSS |
| `VULN_W05` | 다운로드가 문서 id로만 찾음 | `file` 값을 경로에 붙임 → 경로 조작 |

하나라도 켜져 있으면 기동 로그에 경고가 찍힌다. **진단 전에 이 줄로 상태를 확인한다.**

## 4. 구성도·환경 (시스템 구성도)

- 로컬 실행 포트는 **8000**이다(맥 AirPlay가 5000을 점유. 운영 형태의 Gunicorn 127.0.0.1:8000과도 같다).
  거래소에 돌려줄 `auth_url`은 요청의 Host가 아니라 **`PUBLIC_BASE_URL`**로 만든다. (D38, D35)
- A사 → 모의 통신사는 **TLS + 인증서 고정**이다. 시스템 신뢰 저장소가 아니라 통신사 인증서 파일
  하나만 신뢰한다(`CARRIER_CA_BUNDLE`). 호출 타임아웃 5초, 실패는 P05 → HTTP 503. (D43, D44)
- 모의 통신사는 별도 앱·별도 DB(SQLite)·별도 키·별도 TLS를 쓰지만, **CI 계산식과 암호문 형식은
  A사 공통 모듈을 그대로 재사용**한다. 양쪽이 갈라지면 X-01 대조가 조용히 깨지기 때문이다. (D48)
- **진단 대상 배포본은 `EKYC_ENV=production`으로 띄운다.** 그때만 세션 쿠키 `Secure`·HSTS·
  https 강제가 켜진다(로컬 dev는 http로 띄우므로 끈다). (D22, D29)
- 개발 환경은 **Python 3.11(uv)**, DB는 PostgreSQL 16(docker compose).
  테스트는 기본 SQLite 메모리, `TEST_DATABASE_URL`을 주면 PostgreSQL로도 돌린다. (D13, D20, D37)
- 모의 진위확인은 **HTTP 라우트가 없다**(앱 내부 함수). 테스트 문자 수신함은 허용 IP만 열고
  진단 범위에서 제외한다. (D3)

### 공개 회사 홈페이지 추가 (신규)

구성도에 **공개 노출면**이 없었다. 인증창은 위탁사 요청으로만 열리고 관리자 콘솔은 `/admin` 뒤에 있어,
주소를 모르면 들어갈 수 있는 화면이 하나도 없었다. 실제 수탁사라면 회사 홈페이지가 공개돼 있고
그 자체가 점검 대상이다. (D83, D84)

- 경로: `/`(메인), `/about`, `/services`, `/notices`·`/notices/{번호}`, `/support`, `/privacy`, `/demo`
- **DB 테이블을 늘리지 않았다.** 공지·연혁·FAQ는 코드 안의 고정 데이터다. 13개 테이블 그대로.
- 문의 폼은 내용을 **저장하지 않고** 접수번호만 돌려준다(실습 환경에 개인정보를 남기지 않는다).
- 회사·대표자·주소·실적 수치는 전부 가상이고, 모든 화면 최상단에 그 사실을 띄운다.
- `/privacy`의 보유기간·안전조치는 **실제 구현값과 맞췄다.** 컨설팅 산출물의 처리방침 초안으로 쓸 수 있다.
- **자료실(`/library`)과 문의 저장을 더했다(D90).** 표 2개(`site_inquiries`, `site_documents`)가
  11장 13개와 별개로 생긴다. 문의는 담당자 연락처 수준만 받고 개인정보 흐름에 들어가지 않으며,
  자료실 문서는 전부 공개 문서다. 금취분평 웹 항목(SQL 인젝션·저장형 XSS·경로 조작)을
  재현할 대상을 만들기 위한 것이다.

### 모의 PASS 앱 (기기 등록) 추가

인증번호 수신함의 열쇠를 평문 파일에서 복붙하던 것을, **통신사 명의 확인을 거쳐 발급받는** 경로로 바꿨다.
실제 흐름에서 "본인 명의 휴대폰을 들고 있다"가 수신함의 열쇠라는 구조를 그대로 옮긴 것이다. (D85)

- MC-03을 통과하면 수신함 키를 새로 발급한다. **번호당 기기 하나만 유효**하다.
- 수신함과 기기 등록은 D3대로 실습 전용·진단 범위 제외이고 허용 IP 제한이 그대로 걸린다.
- 기존 경로(people.json의 키를 화면에 직접 입력)도 계속 된다.

### 인증 방식 두 가지 (위탁/수탁 경계에 영향)

`mode: "DIRECT"`를 쓰면 **인증 화면을 위탁사가 만들고** A사는 서버 간 API로 판정만 돌려준다. (D87)

이 경우 **주민등록번호와 신분증·얼굴 사진을 위탁사가 직접 수집**하게 되므로, 동의 수집과 안전조치
책임이 위탁사로 옮겨간다. 위·수탁 경계도와 개인정보 처리방침을 함께 손봐야 한다.

반대로 기본값(`REDIRECT`)에서는 위탁사가 그 정보를 **아예 보지 않는다** — 수탁 구조의 핵심 장점이다.
진단 관점에서도 차이가 크다: DIRECT로 옮기면 W-02(CSP·XSS)·W-03(CSRF)·W-07(토큰·세션)·
W-11(인증번호 제한)·W-16(성명 서버 고정)이 전부 위탁사 범위로 넘어간다.
